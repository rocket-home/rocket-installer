# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

**rocket-installer** — установщик и менеджер эксплуатации хаба умного дома Rocket Home
(zigbee2mqtt + mosquitto + мост в облако) для Ubuntu/Debian. Ставится одной командой
`curl -fsSL https://rocket-home.ru/install.sh | bash`, дальше машиной управляют цели `make`
или TUI-команда `rocket`.

Пользовательская документация живёт **не здесь**, а в репозитории janus
(`docs/source/installation/*.rst`, публикуется на rocket-home.ru/docs). Меняешь поведение,
про которое там написано, — правь и там, иначе страница начнёт врать.

## Команды

```bash
make help          # все цели с описанием — первый источник правды
make test          # node --test (TUI) + tests/run.sh (sh-тесты). Гонять перед каждым коммитом
make lint          # shellcheck --severity=warning по всем скриптам, install.sh и bin/rocket
make setup         # визард первичной установки (то же: rocket → «Установка (визард)»)
make up / down     # запуск с пересозданием / остановка стека
make status doctor smoke   # состояние, диагностика, сквозная проверка
make update        # обновление zigbee2mqtt по матрице совместимости
```

`shellcheck` в системе может отсутствовать — тогда `make lint` падает с `command not found`.
Ставить пакет необязательно: переносимый бинарник с
`github.com/koalaman/shellcheck/releases` разворачивается в любой каталог и добавляется в PATH.

## Два слоя и главный принцип

```
Makefile + scripts/*.sh   — исполняемый слой, работает без Node
scripts/rocket-control/   — TUI (Node ≥18, @clack/prompts), ТОНКАЯ оболочка над make
```

**TUI учит CLI.** Каждый шаг печатает эквивалентную команду (`→ make detect-device`), чтобы
пользователь мог повторить всё руками. Логика живёт в make-целях и shell-скриптах; в TUI —
только вопросы, порядок и печать. Новую функциональность добавляй как make-цель, а TUI пусть
её зовёт.

## Инварианты, которые легко нарушить

Всё ниже — не стиль, а выстраданные живыми прогонами правила. Нарушение каждого уже приводило
к молчаливой поломке, которую не видно ни в тестах, ни глазами.

**JSON-цели отдают чистый stdout.** `detect-device`, `detect-firmware`, `resolve-tag` печатают
в stdout только JSON; всё диагностическое — в stderr (`warn`/`err` из `lib/common.sh` уже так
делают). Любая лишняя строка ломает разбор.

**Дочерний make не наследует make-переменные.** `lib/make.mjs` запускает потомка через
`childEnv()` (вычищает `MAKELEVEL`, `MAKEFLAGS`, `MFLAGS`, …) и с `--no-print-directory`.
Иначе GNU Make считает себя под-make, включает `-w` и печатает `make[1]: Entering directory`
в stdout — ровно туда, откуда читается JSON. Не вырезай баннер регуляркой: он локализуется
и неотличим от данных.

**JSON разбирается только через `captureJsonStep`** (`prompts.mjs`). Голый `JSON.parse` и
молчаливый `catch { return null }` запрещены: именно так «мастер не видит координатор» дожил
до пользователей, выглядя как честное «ничего не найдено». Неудача обязана печатать строку
и складывать сырьё в `data/rocket-tui.log` (`lib/debug.mjs`).

**`io.mjs` — единственная точка импорта @clack.** Версия 0.7 не принимает `input`/`output`
в опциях промптов, а `@clack/core` снимает `process.stdin` на импорте — прокинуть туда свой
поток нельзя. Терминал добывается иначе: `rocket.mjs` первым делом зовёт
`ensureInteractiveStdin()` (`lib/tty.mjs`), которая при stdin-пайпе открывает `/dev/tty` и
перезапускает процесс с настоящим fd 0.

**В `install.sh` нельзя делать `exec </dev/tty`.** При `curl … | bash` сам bash дочитывает
оттуда текст скрипта — глобальный редирект украдёт у него остаток файла. Проверять терминал
можно (`[ -t 0 ] || : </dev/tty`), перенаправлять — нет.

**Коды возврата визарда — контракт с install.sh:** `0` готово, `1` шаг не выполнен, `3` нет
терминала, `130` отменено (`lib/exit-codes.mjs`). Визард зовётся как `bin/rocket --wizard`,
а не через `make`: make схлопывает любой код рецепта в свой `2`.

**`load_env` не экспортирует.** docker compose ставит переменные окружения выше `--env-file`,
поэтому экспортированный `.env` замораживает конфигурацию в момент старта скрипта: `make
update` писал новый тег в файл и поднимал старый образ. Нужна переменная в дочернем
процессе — экспортируй её точечно, префиксом команды (см. оба `envsubst` в `gen-configs.sh`).
Читается `.env` буквально, без сорсинга: bash выполнил бы `KEY=два слова` как команду и
раскрыл `$`, то есть скрипт и контейнер видели бы разные значения.

**Точка входа в compose одна — `scripts/compose.sh`.** Там считаются активные профили:
аддоны из `.env` плюс вычисленный `zigbee` (включается по наличию стика, `zigbee_enabled`).
Makefile зовёт её же. Своя строка `docker compose` где-либо ещё = второй, расходящийся набор
сервисов: `make up` поднимет z2m там, где `smoke` его уже не ждёт.

**Строку `adapter:` в configuration.yaml пишет только `gen-configs`**, и только с `FORCE=1`
перезаписывает существующий файл. Поэтому всё, что меняет `Z2M_ADAPTER` или версию образа,
обязано звать `gen-configs` — иначе z2m 2.x не стартует («No valid USB adapter found»).
Данные сети при перегенерации переносит `lib/yaml-preserve.sh`: устройства, группы и
`network_key`. Потеря `network_key` = пересоздание сети, все устройства паруются заново.

**Проверки ждут healthcheck, а не угадывают таймаут.** `wait_healthy` (`lib/common.sh`)
спрашивает docker о состоянии контейнера и различает «ещё поднимается» и «умер/крэш-луп».
Серия `curl --retry` для этого не годится: z2m 2.x после пересоздания поднимается дольше
любого разумного числа ретраев.

**Матрица совместимости — источник истины** для `resolve-tag`/`update`
(`config/compatibility-matrix.json`). Обновляется при релизах z2m; правила проверяются по
порядку, применяется первое совпавшее.

## Тесты

```
scripts/rocket-control/__tests__/   node --test, моки через __tests__/_harness.mjs
tests/sh/test-*.sh                  самостоятельные скрипты, exit 0 = pass
```

**Моки не ловят целый класс дефектов.** `_harness.mjs` подменяет `lib/make.mjs` и `io.mjs`
целиком, поэтому `runMakeCapture` всегда возвращает идеально чистый JSON, а реальный `spawn`
и реальный stdin в таких тестах не участвуют вовсе. Всё, что живёт на границе процессов
(окружение потомка, терминал, коды возврата), проверяется тестами **без харнесса** — см.
`make-env.test.mjs` (реальный spawn под `MAKELEVEL=1`) и `no-tty.test.mjs` (запуск процесса
с пайпом на stdin). `node --test` запускает каждый файл отдельным процессом, поэтому файл без
`installMocks()` работает с настоящими модулями.

Швы для тестов (переменные окружения, а не пользовательские настройки):
`ROCKET_ROOT`, `ENV_FILE`, `ROCKET_DEV_ROOT`, `ROCKET_UDEVADM`, `ROCKET_PROBE_CMD`,
`ROCKET_TTY_DEVICE`, `ROCKET_LOG_FILE`, `ROCKET_HEALTH_POLL`, `SMOKE_Z2M_TIMEOUT`.
`docker` в sh-тестах подменяется заглушкой через `PATH` — так проверяются и порядок вызовов,
и то, какой образ реально поднялся.

Полезный приём: написав тест на регрессию, **верни дефект и убедись, что тест краснеет**.
Тест, который зелёный в обоих случаях, ничего не стережёт.

## Релиз

Автоматизации нет: релиз — это аннотированный тег `vX.Y.Z` в `origin/main`
(`github.com/rocket-home/rocket-installer`). Формат сообщения устоявшийся: заголовок
`vX.Y.Z — <суть>`, тело с разбором находок, последняя строка со сводкой тестов
(`Тесты: node --test N, sh M, shellcheck чист.`).

Порядок важен. `rocket-home.ru/install.sh` — это 302 на
`raw.githubusercontent.com/rocket-home/rocket-installer/**main**/install.sh`, то есть новый
`install.sh` доезжает до людей сразу после пуша в main; а сам инструмент в `/opt/rocket-home`
ставится по **последнему тегу**. Поэтому пуш main и пуш тега делаются подряд, без паузы —
иначе свежий `install.sh` будет работать со старым деревом. Версию в `package.json` держи
синхронной с тегом.

Перед тегом: `make test`, `make lint` и живой прогон в чистой ВМ с координатором — моки не
заменяют проверку того, что установка доходит до конца.

## Стиль

- Комментарии на русском и объясняют **почему**, а не что: «MAKELEVEL заставляет make печатать
  баннер в stdout», а не «чистим переменные».
- Чинить источник, а не маскировать симптом. Лишняя строка в stdout лечится тем, кто её
  печатает, а не фильтром у читателя.
- Отказ обязан объяснять себя и предлагать следующий шаг. Сообщение, приписывающее чужую
  ошибку докеру, хуже, чем отсутствие сообщения.
- Не добавляй зависимостей ради удобства: `scripts/*.sh` должны работать на голой системе,
  где есть bash, docker, jq и gettext-base.
